# vector-index

从零实现 **HNSW**（分层可导航小世界图）与 **IVF-PQ**（倒排文件 + 乘积量化），
把「检索质量 / 构建耗时 / 内存 / 延迟」四组数字放在同一张表里对照。

**零第三方依赖 —— 连 numpy 都不用**，核心算法只用 Python 标准库；
FastAPI 只出现在 HTTP 边界（`app/main.py`），由 CI 里的门禁脚本强制。

```
暴力检索（精确）   recall@10 = 1.0000   p50 = 0.51 ms   扫描 800 点/查询   内存 100 KB
HNSW（图）        recall@10 = 1.0000   p50 = 0.43 ms   扫描 422 次/查询   内存 200 KB
IVF-PQ（量化）    recall@10 = 0.6560   p50 = 0.37 ms   扫描 244 次/查询   内存  17 KB
                 threshold_recall = 0.9880
```

（800 点 × 32 维 clustered 数据集，seed=42，可逐位复现）

这两个召回率数字放在一起就是本项目最重要的一个观察：
**IVF-PQ 的标准召回率只有 0.66，但门槛召回率是 0.99** ——
它返回的邻居"距离都够近"，只是不总是那同一个集合。
在并列多的数据上，拿标准召回率给 IVF-PQ 打分是错的。

---

## 为什么不用 faiss / numpy

* **内存是这个项目要量化的指标之一。** 用 `array('f')` 而不是 `list[float]`，
  向量本体内存降到约 1/5（32 维 = 128 字节 vs 约 640 字节）。
  引入 numpy 后这个数字就变成"numpy 内部怎么存的"，反而看不见了。
* **每一步算法都直接暴露在代码里**，可以被单测逐项验证
  （"k-means 第 3 次迭代后质心还在动吗"、"启发式丢弃了哪些边"）。
  faiss 是黑盒，这类断言写不出来。
* **性能落差没有想象中大**：距离计算用 `math.sumprod`（Python 3.12+ 的 C 实现），
  实测 1.54 µs/次，比手写 `for+range` 循环（4.46 µs）**快 2.9 倍**。
  纯 Python 一样能把单次查询压进亚毫秒。

诚实的边界写在下面的「已知限制」里。

## 架构

```
app/
  metrics.py     距离度量、向量容器、内存核算        ← 所有"远近"判断的唯一来源
  dataset.py     可控结构的合成数据集
  bruteforce.py  精确 kNN + 两种召回率口径          ← 基线，也是真值来源
  hnsw.py        分层图索引
  ivfpq.py       倒排 + 乘积量化
  benchmark.py   召回率 / 构建耗时 / 内存 / 延迟分位数
  registry.py    数据集与索引的登记（LRU 上限）
  main.py        FastAPI 路由                       ← 唯一允许第三方依赖的模块
web/index.html   对照实验界面（原生 JS + SVG）
```

依赖方向严格单向：`main → registry → benchmark/hnsw/ivfpq → bruteforce → metrics`。
`scripts/check_core_isolation.py` 用三层手段保证这件事：

1. **静态 AST 扫描** —— 顶层 import 必须全部来自标准库，报错精确到行；
2. **动态导入拦截** —— 子进程里装 meta-path finder 拦掉一切非标准库模块，
   再真的 `import_module`。能抓到静态扫描漏掉的间接依赖：
   注入一个 `import numpy` 后，除声明模块本身，还暴露出 6 个下游模块被"传染"；
3. **反向校验豁免名单** —— `app.main` 被豁免，就必须真的依赖 fastapi。
   没有这条，豁免名单只会膨胀，规则名存实亡。

## 设计里真正难做对的几件事

### 统一的「越小越近」

L2、cosine、内积三种度量的方向不同，全部在 `metrics.py` 收敛成"距离越小越近"：
L2 用平方欧氏；cosine 用 `1 - cos`（两侧都归一化）；内积取负号。
下游的图、量化、top-k 代码因此只需要写一次。
距离**不** clamp 到 0 —— 近重复向量的 1e-9 级负距离是排序的稳定信号，
clamp 掉之后并列打平就变成随机的。

### 两种召回率口径

* **标准召回率** = |ANN ∩ 精确| / k，分母固定 k（不是 |精确|，否则库里点少时召回率虚高）；
* **门槛召回率** = ANN 距离 ≤ 第 k 名门槛的比例，且必须用 **ANN 自己算的距离** ——
  重算精确距离会掩盖"PQ 近似距离系统性偏大"这类问题。

并列多的数据上两者会分岔（见开头数字）。benchmark 同时给出两个，
而且断言"门槛召回 ≥ 标准召回"是**测试**的一部分，不是文档。

### HNSW 的三个细节

论文一笔带过、写错一个就废掉召回率的地方：

1. **多样性启发式（Algorithm 4）**：候选 c 只有当「c 到查询的距离 < c 到任一已选邻居」时保留。
   只按距离截断会把所有邻居塞在一个方向上，图失去跨簇连通性。
2. **剪枝也用启发式**：系统性删最远的边等于系统性保留同方向的边。
3. **早停**：最近候选比结果集里最差的还远就停。
   不加这一条，搜索退化成"把连通分量走一遍"——结果一样，耗时差一个数量级。

实测：600 点 m=16 时平均每节点只有 **13.97 个边槽位**，远低于 M0=32 的上限 ——
这个差距就是启发式在剪枝的直接证据。

### IVF-PQ 的诚实账本

* **不保存原始向量**：每个向量压成 m 个字节，这就是召回率有上限的原因 ——
  信息已经丢了，不是算法不聪明。
* **压缩比给两个口径**：`codes_only = 4d/m`（默认 16×，n 大时才逼近），
  `index_total`（含码本/倒排表/粗质心）。1200 点实测只有 5.22× ——
  码本是 O(nlist·d) 的**固定开销**，小数据集上把理论值吃掉一大半。
  n=100k 时才接近理论值。混用两个口径会得出互相矛盾的结论。
* **kmeans 的空簇必须显式重置**：空簇永不分到点，等于永久浪费一个聚类名额。
* **内积度量在构造时直接拒绝**：内部按 L2 量化，内积没有可换算的恒等式，
  放行会得到"看起来能用"但排序毫无意义的结果。cosine 可以（归一化后
  `cos 距离 = ‖a-b‖²/2`，恒等式精确成立）。

### 内存账里的一个反直觉事实

「HNSW 的内存几乎全是边」**不是无条件成立**：
边开销 ≈ `8 × M0` 字节/节点，向量 ≈ `4 × d` 字节/节点，谁更大取决于 `M0 vs d/2`。
默认 M0=32、d=32 时两者几乎持平；d=128 时向量重新成为大头。
这个项目早期文档写死"几乎全是边"——那是在 d=8 的小数据集上得出的，
换真实维度就错。基准结果把两个数都列出来，不含糊。

## API

```
GET    /api/health                    健康与版本
GET    /api/options                   合法取值（前端下拉框数据源）
POST   /api/dataset                   生成数据集（count/dim/kind/metric/seed/...）
GET    /api/dataset                   列出
GET    /api/dataset/{id}              详情
DELETE /api/dataset/{id}              删除
POST   /api/index/{id}                构建索引（engine + params）
GET    /api/index/{id}/{engine}       索引快照
POST   /api/search                    单次检索（ANN vs 精确，两种召回率 + 延迟对比）
POST   /api/benchmark                 三引擎对照评测（含 ef/nprobe 扫描曲线）
GET    /api/benchmark?count=...       GET 版本，浏览器地址栏直接跑
```

错误语义：参数越界 / 未知枚举 → `422`；资源不存在 → `404`；
上游算法抛的异常不会漏成 `500`（e2e 里逐项断言）。

## 基准怎么读

| 列 | 含义 | 怎么用 |
|---|---|---|
| 召回率 | 集合交集 / k | 看趋势，别看单点 |
| 门槛召回 | 距离 ≤ 门槛的比例 | 并列多时**以它为准** |
| p50 / p95 / p99 | 线性插值分位数 | p95 与 p50 的差距决定能不能上线 |
| 距离/查询 | 一次查询的真实工作量 | 比 QPS 更能解释"为什么快/慢" |
| 内存 | 分项列出 | 容量规划用它，不用 QPS |

扫描曲线（ef / nprobe）是这套基准里最有决策价值的部分：
「把 ef 从 32 调到 128，召回率从 0.92 到 0.99，p95 从 0.3 ms 到 0.9 ms」
——这种关系才是调参的依据，单点数字给不出任何决策。

## 已知限制

* **纯 Python 的 k-means 撑不住大参数**。`nlist` 大于 64 或 `nbits=8` 时
  训练会明显变慢（实测 nbits 4→8 训练时间 ×10）。默认参数偏小是有意的。
* 数据集上限 `count=20000 / dim=512`，入口硬拒绝而不是让它跑几分钟再超时。
* 单进程、单机、无持久化。数据集和索引放在内存里，服务重启即失。
* `ef_search` / `nprobe` 是查询期旋钮，但**构建参数（m / nlist / m / nbits）
  改了就必须重建索引** —— 接口层没有隐式重建。
